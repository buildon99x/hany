# Harness Glossary

> Entry point: `docs/harness/README.md` · Operating playbook: `docs/harness/HARNESS_OPERATING_PLAYBOOK.md`

## Acceptance Case
A Given/When/Then statement that connects a requirement to concrete test evidence.

## Active Turn Time
Sum of intervals between each user text message and the immediately following assistant message within a Phase window. Used by the Effort Ledger as the cost signal for Phase active work; excludes user idle time and session sleep. Computed from per-message timestamps in session JSONL; tool-call durations are not separately tracked.

## Aggregate-Only Input
Keyboard and mouse data reduced to counts, rates, durations, or coarse buckets. It excludes raw key values, typed strings, exact click coordinates, cursor paths, window titles, and app-specific input content.

## Artifact
Any file generated by tests or harnesses, including logs, screenshots, metrics, HTML reports, JSON reports, diffs, and failure bundles.

## Data Inventory
A record of what data a feature collects or stores, why it is needed, where it lives, how long it remains, and how the user can delete it. Template: `docs/harness/DATA_INVENTORY_TEMPLATE.md`.

## Degraded Mode
A product state where part of the system is unavailable, but the app remains understandable, recoverable, and honest about what still works.

## Difficulty Tier
Low / Medium / High classification assigned to a feature before implementation; controls evidence scope. Reference: `docs/harness/FEATURE_DIFFICULTY_TIERS.md`.

## Effort Factor Categories
The six labels used in the Retrospective Effort 분석 section to classify why a Phase exceeded the 30% / 20-minute / 50k thresholds: **탐색** (exploration), **재시도** (retry), **리뷰응답** (review response), **cross-cutting**, **외부 IO**, **컨텍스트 폭주** (context blowup). Multiple labels per Phase allowed.

## Effort Ledger
Phase-scoped table inside `docs/spec/{feat-name}_harness_ledger.md` recording Active Turn Time, wall-clock elapsed, and five-way token usage (input / output / 1h cache-create / 5m cache-create / cache-read). Auto-updated inside `<!-- effort:auto:begin --> … <!-- effort:auto:end -->` sentinel markers via `npm run harness:effort` or PreToolUse hook; threshold marks (`[T]` / `[K]` / `[TK]`) are assigned at retrospective time after the Σ row is finalized. Applies to Medium+ new ledgers only.

## Feature Quality Note
The compact handoff attached to a PR or task summary that lists requirement, UX, stability, privacy, and operational evidence. Template: `docs/harness/FEATURE_QUALITY_NOTE_TEMPLATE.md`.

## Gate Calibration
Evidence that a harness gate can fail for the intended reason, usually through a known-failing fixture, negative sample, or expired-baseline check.

## Loop Budget
The maximum number of repeated automatic fixes or test reruns before the system stops and asks for a new hypothesis or user decision.

## Pause Point
A deliberate checkpoint before risky, long-running, destructive, privacy-sensitive, or broad-scope work continues.

## Quality Gate Matrix
Per-feature traceability table that pins requirements to gates, evidence, blocking mode, and risk. Template: `docs/harness/QUALITY_GATE_MATRIX.md`.

## Resident Stability
The ability of the app to run in the background for long periods without accumulating CPU, memory, handles, timers, logs, queues, or duplicate lifecycle resources.

## Security Boundary
The trust line around local files, secrets, reports, IPC, hooks, plugins, update paths, and external tools. It complements privacy by preventing unauthorized access or disclosure.

## Scrubber
A validation step that scans schemas, logs, reports, artifacts, and storage output for privacy-forbidden fields or content.

## Soak
A long-running test that validates stability over time, usually in nightly or weekly CI rather than local hooks.

## Work Status Snapshot
Compact in-flight status for long-running tasks: goal, current step, changed files, evidence, blockers, next action, pause point. Template: `docs/harness/WORK_STATUS_TEMPLATE.md`.

## Axis Mapping

The harness uses three orthogonal axes that easily get conflated. They describe **different things**, not the same scale:

| Axis | Used in | Values | Meaning |
| --- | --- | --- | --- |
| **Gate cadence** | `QUALITY_GATE_MATRIX.md` | PR · Nightly · Weekly · Release | When a gate runs and what blocks merging vs. release. |
| **Rollout phase** | `IMPLEMENTATION_SEQUENCE.md` | Phase 0 – 5 | Which slice of the harness is being built (fixtures → drivers → oracles → reporters → CI → dashboards). |
| **Day plan** | `HARNESS_PLAN.md` | D1 – D14 | Calendar-day milestones for the initial harness build. |
| **Difficulty tier** | `FEATURE_DIFFICULTY_TIERS.md` | Low · Medium · High | Per-feature evidence scope; selects which gates apply for a given change. |

A feature has one **tier**, runs through a subset of **gates** at a given **cadence**, and contributes to a **rollout phase** of the harness itself.
